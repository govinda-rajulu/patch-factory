## 1. Releases: duplication, bloat, obsolete targets, and retention

### Policy and execution

* `src/etc/release_retention.py` is explicitly **preview-only**: it has no deletion/apply mode. It keeps the **two newest dated releases per configured tag prefix**, and protects frozen/manual/unknown/ambiguous records plus drafts/prereleases and explicit keep markers. `FROZEN = {'truecaller-v26.10.6'}` is hard-coded.
* `RECOVERY.md` repeats that policy and says evidence JSON is only metadata recognition, not verification; release deletion removes assets, tag deletion is separate, and backups/approval precede cleanup.
* `.github/actions/release/action.yml` runs the script after publication with `--output retention-preview.json --summary "$GITHUB_STEP_SUMMARY"`; this is a running **preview**, not an automatic prune. The historical `docs/review/retention/CLEANUP-2026-09-26.json` records an owner-approved cleanup of 47 old releases and says tags remained. It is historical evidence, not a current deletion authorization.
* `src/targets.json` at this commit has 15 enabled prefixes: `youtube-morphe`, `yt-music`, `adguard`, `gg-photos`, `tc-combo`, `prime-video`, `es-file`, `facebook`, `instagram`, `reddit`, `hotstar`, `edge`, `mx-player`, `telegram`, `key-mapper`. OWNER.md says SonyLIV/ZEE5 and standalone Truecaller are retired; standalone frozen `truecaller-v26.10.6` is protected forever. No SonyLIV/ZEE5 current release was observed in the inspected API pages.

### Findings

* The committed cleanup evidence has 47 deleted-release records: same app/version rebuilds, generally differing APK hashes but often identical APK byte sizes. They are retained in `RELEASES.tsv` as `dup-older` evidence, not as a proposal to delete again.
* Current API excerpts show repeated same-version rebuilds, e.g. `yt-music-v9.40.51-b20261006...` followed by `...b20261007...`, and multiple `mx-player-v1.93.4` builds. These are legitimate patch-only rebuilds at the artifact level but are duplicates for retention purposes once outside the newest two.
* The current API inventory was paged with `per_page=100&page=1` and `page=2` (page 2 was empty), and additionally inspected in `per_page=10` pages 1–10 (pages 11–20 empty). The tool returned truncated bodies for several large pages; exact rows that were available are preserved in TSV, while rows whose body/asset details were not available are explicitly marked `unknown`. Do **not** infer a total or delete from a truncated page. This is the material limitation of the release table.
* No current release was classified `no-asset` from the inspected excerpts; legacy date-only releases do have APK-only assets and are protected as ambiguous/nonstandard by the policy. No current retired-target release was observed in the inspected excerpts. `truecaller-v26.10.6` is explicitly `keep-protected`.

### Safe proposal (not an execution request)

After a fresh API inventory, independent asset backup, and checking portal/Obtainium references: propose only older dated CI releases beyond the newest two per enabled prefix, excluding drafts/prereleases, frozen/manual/unknown/ambiguous records, and anything still linked by a user’s saved portal/release URL. Do not delete the newest enabled-target release, even if it is a same-version rebuild. Do not delete `truecaller-v26.10.6`; do not delete tags merely because assets were removed. The existing preview output should be used as the candidate list and reviewed against a fresh fingerprint.

## 2. Release-note duplication and generator ownership

### Repeated blocks

The structured notes are generated by `src/build/release_notes.py`; `.github/actions/release/action.yml` passes `steps.meta.outputs.notes` to `ncipollo/release-action` as the body. The generator repeats these blocks in every structured release (the exact count varies with the number of structured releases; the API excerpts and retention record show both legacy and structured eras):

1. **Checks and limitations** (~374 bytes before release-specific substitutions):
   > CI checked APK identity, declared minimum Android API, native payloads, applied patch names and its configured signing certificate.\n   > Not phone-tested by this pipeline; not proof of original-publisher authenticity or installed-app compatibility.\n   > Same-version patch-only update delivery in Obtainium remains limited. New build does not necessarily mean a new app version.
2. **Stable help / install warning** (~181 bytes in the generator skeleton):
   > ## Help and stable information\n   > [Install, updates, source types and status meanings]\n   > No automatic uninstall, import migration or device-protection bypass is required or recommended.
3. **Applied-patch heading and lead-in** (~50 bytes before patch count/list):
   > ## Applied patches (N)\n\n All applied patch names
4. **Download evidence heading** (~89 bytes before file/hash substitutions):
   > ## Download evidence\nFile: `APK`\nSHA-256: `HASH`\nCI signing certificate SHA-256: `SIGNER`
5. The release body always ends with one `[pf-release-v1]: # "<base64>"` structured marker. This is intentionally machine-readable duplication of the summary and is consumed by `release_notes.decode()` and retention classification; it should not be hand-edited.

The older legacy notes repeat a different boilerplate in each release: `Patch provider(s): …`, `App version … · arm64-v8a`, `**Applied patches**`, `Patch bundle …, built …`, `Verify before installing: sha256sum …`, and `Built in public CI with morphe-desktop.` The generator’s structured format supersedes that prose but old release history must remain readable. Consolidation recommendation: keep one generated canonical note template; put long install/status explanations in `docs/guide.md`, and have notes link to it rather than repeating policy prose. Preserve the structured marker and evidence lines because portal/retention/tests consume them.
