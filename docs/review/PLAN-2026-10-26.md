## 0. My call on "one W16n for everything"

Plan once, decide once, launch many. Not one packet.

- Why not one: W15g moves the release key across a new trust boundary and needs a full all-app
  batch plus your phone test; W17 is about 1,000 to 1,700 lines, W18 another 900 to 1,500. In one
  packet a single red smoke blocks the docs and security fixes, a revert takes everything out, and
  reviewers cannot finish shards that big (REVIEW-METHOD round 6 lesson).
- What you get instead: every decision answered now (section 7), so there are no question rounds
  later. After that each packet is: launcher, you paste RESULT, next launcher.
- Order: P0 probe -> W16n -> W16o -> W15g -> W17a -> W17b -> W18.

## 5. Method, and what changes this time

Kept from REVIEW-METHOD.md: independent agents, one lens each, full populations in shards, second
pass on fixes, exit when a fresh set finds no HIGH or MED, then the full suite and the six rehearsals.

New in this chat, written into REVIEW-METHOD.md by W16n:
1. Cross-file lens. F2 lived between two workflows; no shard saw both. New reviewer: shared resources
   (branches, issues, concurrency groups, artifact names, state files), every writer and reader of each.
2. Re-rate every agent HIGH against the code before acting. This round: 3 of 9 HIGHs were overstated.
3. Live-verify what the API can show (watch-state tree, issue state, run times) before writing it down.
4. Agents must cite the cron line, not restate it (an agent added a 06:23 cron that does not exist).
5. Probe before patch: a live read (P0) settles a root cause before code is written (Alastor `-x`).
