## 1. What W15g is, and the owner phone test

W15g moves third-party Morphe patch execution out of the signing boundary: a read-only, secretless `patch` job runs the pinned patcher with `--unsigned`; a first-party-only `sign` job alone decodes the CI keystore and uses `apksigner`; and a keyless `publish` job verifies and publishes the signed artifact. This addresses the current HIGH finding that the single job decodes the release keystore, passes its password to the patcher, and publishes with a write token. The split must preserve the live CI certificate fingerprint `08480f6649a2be33ff3cccacce07454761d5fb9abe65f1e2caeeb782e382d050` from [`src/build/ci-signer.json`](repo/src/build/ci-signer.json): changing it is a signer rotation and breaks in-place updates and Obtainium pins. The design changed from a throwaway BKS signer to Morphe 1.19/Patcher 2.0 `--unsigned`; the capability must be probed and absence must hard-stop, never fall back to signed patching. Sources: [W15G-MAP.md](repo/docs/review/W15G-MAP.md), [OBTAINIUM-SIGNER-2026-10-27.md](repo/docs/review/OBTAINIUM-SIGNER-2026-10-27.md), [SIGNING-SPLIT.md](repo/docs/review/SIGNING-SPLIT.md).

**Owner phone test after CI gates pass:** publish one small target, then install its APK **over the currently installed copy** (do not uninstall/reinstall). Record package identity, Android's update success, launch and the relevant update path, signer/certificate continuity expectation, and data/login behavior. This is required device proof, not replaceable by CI. On Android 11/12 keep Obtainium's signer pin; the Android 10 main phone uses the documented no-pin import because Obtainium's certificate read is unavailable there, while Android itself still enforces same-signer updates. See [OBTAINIUM-SIGNER-2026-10-27.md](repo/docs/review/OBTAINIUM-SIGNER-2026-10-27.md) and [KT-2026-10-28.md](repo/docs/review/KT-2026-10-28.md).

## 3. Risks and exact gates/tests

### Load-bearing risks

* **Signer continuity (HIGH):** the expected DER certificate SHA-256 is `08480f6649a2be33ff3cccacce07454761d5fb9abe65f1e2caeeb782e382d050`. The signed APK must remain that signer. A changed signer breaks Android in-place updates for every installed app; Obtainium’s pinned `allowedSigningCertHashes` also rejects it on supported Android versions. Do not edit `ci-signer.json` in W15g.
* **Secret exposure (HIGH):** today `Decode keystore` precedes patching, `build.sh` captures it before patching, `patch_target.py` puts passwords in argv, and `utils.sh` has legacy `eval` paths. A workflow-level secret declaration is not itself an injection; every job/step reference and child env must be audited.
* **Wrong or cross-run artifact (HIGH):** an unsigned APK from another target/run/attempt, or a mutated handoff, could be signed and published. Exact run-scoped artifact names, action digest mismatch checks, source/target/run/attempt binding, and SHA checks are mandatory.
* **Signature-side byte mutation (HIGH):** signing may alter expected ZIP metadata. Preserve the unsigned file, sign to a separate output, check zipalign before signing, and compare ZIP members excluding only signature material (`META-INF/*.RSA|DSA|EC|SF` and `META-INF/MANIFEST.MF`).
* **Patcher capability/behavior (HIGH):** a jar without `--unsigned` must stop before patch. Never “retry without the flag” or reintroduce a key into patch.
* **Receipt boundary (HIGH):** publish no longer has the patcher jar, bundles, source APK, or request ledger. The patch sealed draft must carry the needed consumed-input/declaration/effective evidence; publish adds unsigned→signed evidence and still verifies release/tag/asset/read-back.

### Exact pre-merge tests/gates

1. **Static secret audit:** workflow parse/contract tests prove patch has no `KEYSTORE_B64/PASS/ALIAS`, no `src/ks.keystore`, and no write permission; sign is the only job with decode/capture/sign secret references; publish has no signing secret and only its normal GitHub token. Search all production patch code to prove no `KEYSTORE_PASS`, `KEYSTORE_ALIAS`, `--keystore-password`, or credential-bearing `eval` remains in `utils.sh`, `build.sh`, `patch_target.py`, or attempt wrapper. Assert the patcher child allowlist excludes `GITHUB_TOKEN` and all secrets.
2. **Unsigned capability hard stop:** a test jar/help fixture with no literal `--unsigned` makes the capability probe fail before any patch invocation; a fixture with it proceeds. The production command must include `--unsigned` and omit all keystore options. No fallback path is accepted.
3. **Signer-before-sign gate:** in sign only, decode B64 with the existing truncation check (>3000 bytes), run `capture-signer` using `keytool -storepass:env KEYSTORE_PASS`, compare exported DER hash to `ci-signer.json`, and stop before `apksigner` on mismatch. Assert the password is not in argv, logs, reports, or artifacts.
4. **Handoff identity gate:** download exact `patch-output-${target}-${run_id}-${run_attempt}` with `digest-mismatch: error`; require target/source commit/run/attempt equality. Compare report path/bytes/SHA to the downloaded APK and stop before signing on any mismatch. Check unsigned ZIP alignment and preserve that file.
5. **Byte/member gate:** after `apksigner sign --out signed.apk unsigned.apk`, compare unsigned/signed ZIP entries and bytes for every entry except the explicitly allowed signature files; assert the signed output is not the unsigned path. This proves the payload is unchanged, rather than merely trusting a signer log.
6. **Exact signing gate:** assert the sign command has `--ks`, `--ks-key-alias`, `--ks-pass env:KEYSTORE_PASS`, `--key-pass env:KEYSTORE_PASS`, `--v1-signing-enabled true`, `--v2-signing-enabled true`, `--v3-signing-enabled true`, `--out`, and separate input/output paths. Then run `apksigner verify --verbose --print-certs`; require exactly one signer and exact public fingerprint match.
7. **Signed contract gate:** `release_contract.py` accepts only the split signed schema with `signing_split: true`, both unsigned/signed records, unsigned and signed hashes, signer pin, source commit, run ID and attempt. It must reject a legacy unsigned report and reject a signed report whose output/hash/path does not match the downloaded artifact.
8. **Receipt/publication gate:** patch sealed draft includes target, commit, run/attempt, consumed records, declaration/effective hashes, unsigned SHA and identity report. Publish receipt includes unsigned and signed SHA, checks effective hash, release/tag/asset identity, no overwrite, read-back, and successful `Patch <target>`, `Sign <target>`, and `Publish <target>` job/step coverage.
9. **Rollout gates from the records:** run the full 17-target `batch-patch.yml` with `publish=false`; each target must patch unsigned and sign successfully with no release. Then publish one small target from main and verify release asset SHA, release contract, receipt read-back, and publish secretlessness. Finally perform the owner phone test above. These are explicitly required by [W15G-MAP.md](repo/docs/review/W15G-MAP.md).

## 4. Size and packet decision

This is **not** a small workflow-only change. Planning estimate: one substantial implementation packet covering roughly three workflow jobs, a new artifact/report handoff, identity/release/receipt refactors, the three legacy shell call sites, and the listed contract fixtures—approximately 1,000–1,500 changed lines including tests, followed by a full suite, a 17-target nonpublishing rehearsal, a publishing rehearsal, and a phone test. The dominant effort/risk is not line count: it is proving the secret boundary and receipt evidence across reruns and provider fallback attempts.

It should **ship alone next**, exactly as the owner rule says in [KT-2026-10-28.md](repo/docs/review/KT-2026-10-28.md): “W15g signing split goes alone next.” Do not combine implementation with provider, portal, docs, cleanup, or issue housekeeping before its rollout proof; unrelated changes make the signer/secret/artifact evidence harder to attribute. Low-risk docs/portal/issue housekeeping can be a later packet (or a separately reviewable docs-only packet) after W15g’s full batch, publish rehearsal, and phone proof are recorded.
