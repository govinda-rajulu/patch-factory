# R4 — W15g signing split, patch-job lens

**Scope reviewed:** `git -C (assistant sandbox) diff 74addf3..HEAD -- src/build/build.sh src/build/build_attempts.py src/build/patch_target.py src/build/execution_inputs.py src/build/utils.sh src/build/artifact_identity.py`, plus the current implementations and all repository/workflow call sites for the patch path. Context checked: `BRIEF.md`, `MORPHE-SOURCE.md`.

## Verdict

I found **no HIGH-severity patch-job regression**. The old identity gates are still run on the unsigned APK; only signer/cryptographic checks moved to the first-party Sign job. The only actionable finding is a **LOW** robustness issue in the support probe: the probe intentionally ignores `java ... --help`'s exit status and accepts any output containing `--unsigned`. This fails closed for a missing Java or an ordinary bad JAR, but can accept a broken invocation that prints a misleading help-looking line and only fail later at the real patch invocation.

## Findings

### LOW — help probe suppresses the Java exit status

**WHERE:** `src/build/build.sh:324-330`.

**WHAT:**

```bash
PHELP=$(java -jar "$PJAR" patch --help 2>&1) || true
if ! grep -qF -- '--unsigned' <<<"$PHELP"; then ...; fi
```

The literal long option is the right picocli probe (`PatchCommand` declares `--unsigned`; help may wrap the description, so matching the option itself is appropriate). `set -uo pipefail` does not create a problem here: the help text is captured in a command substitution, the `|| true` is explicit, and the here-string grep is in an `if !` condition. The JAR inventory check is also fail-closed for zero or multiple normal filenames (`ls morphe-desktop-*.jar`, then one output line), and the probe happens after input capture but immediately before `patch_target.py`, not after patching.

However, `|| true` discards whether Java successfully executed the JAR. If a malformed/broken JAR (or a wrapper named `java`) emits `--unsigned` and exits nonzero, the build passes this gate and then fails only at the real patch subprocess. If `java` is absent, the shell's error text does not contain `--unsigned`, so the build refuses; the behavior is safe but reports `UNSIGNED_UNSUPPORTED` rather than “Java unavailable.”

**WHY:** This is availability/diagnostic robustness, not a signing bypass: a bad Java/JAR cannot produce a successful patch output merely by passing this grep, because the subsequent `patch_target.py` invocation still runs the actual command and checks its return code.

**FIX:** Explicitly check `command -v java`, preserve the help command's status (picocli's `patch --help` should be a successful invocation), and then match `--unsigned`; if compatibility with a known nonzero help convention is required, allow only that documented status rather than all failures.

### LOW (observation, not a dropped old check) — stale META-INF signature entries are recorded, not rejected

**WHERE:** `src/build/artifact_identity.py:402-438`; `src/build/sign_apk.py:194-206`.

`verify_unsigned` records up to 50 matching `META-INF` signature entries as `unsigned.signature_files_present`, but does not require that list to be empty. Sign's entry comparison excludes all entries matching `SIGNATURE_FILE` on both sides. This is consistent with the split design and is not a regression from old `verify_final`: old `verify_final` did not require an unsigned APK to have no signature entries either; its signature-related work was apksigner verification and signer identity. If the intended invariant is “the patcher output must contain no old v1 signature files,” an explicit Sign handoff check would be needed, but that would be a new requirement, not a missing old check.

## Old `verify_final` checks: retained versus moved

Old `verify_final` (the version at `74addf3`) checked:

* structure;
* `.build-inputs.json` schema and target;
* current `HEAD` equals captured source commit;
* captured repository/tool/bundle/input/ledger records;
* input recipe and source-fallback receipt;
* prepared dependency consumption when requested/matched;
* keystore certificate equals the captured expected certificate;
* target package/min-SDK contract;
* one release APK (the old code selected the first; the new code is stricter and requires exactly one);
* output metadata, version and architecture;
* at least one applied patch;
* apksigner cryptographic verification, exactly one parsed signer and expected signer certificate.

`verify_unsigned` retains every non-signature item above at `artifact_identity.py:407-432`. The old keystore/signer pieces are moved rather than deleted:

* `src/build/sign_apk.py:145-158` calls `check_keystore_pin` before `apksigner sign`.
* `src/build/sign_apk.py:218-246` refuses signing material at verification, runs apksigner verification, parses the signer and calls `validate_signer`; it also verifies schemes, unsigned/signed hashes, entries, alignment, zipalign and unchanged metadata.
* `src/build/release_contract.py:25-76` rechecks the split report, run binding, signer pin, signature evidence, manifest, architecture, APK record and release metadata before publication.

Thus the patch-side identity report no longer invokes `cert_from_keystore` or `apksigner`, but those are now first-party Sign/release gates. The current workflow order is patch unsigned verification, then artifact handoff, then Sign verification/release-contract verification, then Publish.

## `--unsigned` probe and patch invocation details

* **Picocli form:** `java -jar "$PJAR" patch --help` is the correct subcommand help shape for the declared `--unsigned` option. Matching the literal option avoids dependence on description wrapping.
* **Exit status:** the probe ignores it (`|| true`), which is the LOW finding above. The real patch subprocess return code remains checked in `patch_target.py` and `build.sh`.
* **`set -uo pipefail`:** no unsafe pipeline is used by the probe. `grep` is tested under `if !`; the command substitution is protected by `|| true`; unset-variable handling is not triggered by the quoted variables in this block.
* **JAR glob:** `build.sh` requires exactly one normal `morphe-desktop-*.jar` output line before probing. Earlier `github_patcher.py`/cleanup logic also reduces the inventory to one verified JAR. `capture_inputs` independently requires one JAR. No production path was found that leaves multiple ordinary patcher JARs intentionally for this block.
* **Timing:** the probe is after download/selection/input capture and before `patch_target.py`. It can therefore spend download/capture time before discovering an old patcher, but it never invokes the patcher before checking help. This is an availability/cost issue only.
* **Java presence:** there is no explicit `command -v java`; a missing Java produces empty/nonmatching help and refuses with `UNSIGNED_UNSUPPORTED`. This is fail-closed, though the diagnostic could be more precise.
* **Actual argv:** `patch_target.command` requires `PF_UNSIGNED=true`, appends `--unsigned`, and omits all four keystore/password options. Its subprocess environment allowlist excludes `KEYSTORE_*` and the workflow token. The parent `build_attempts` environment passes `PF_UNSIGNED=true` and strips all names beginning with `KEYSTORE` before invoking `build.sh`.

## Keystore and caller audit

### Patch job paths

No remaining patch-job code expects or reads `src/ks.keystore` or `KEYSTORE_*` as a signing input:

* `build_attempts.py:185-191` refuses any incoming `KEYSTORE*` variable; `:229-231` strips them again and sets `PF_UNSIGNED=true` for each build attempt.
* `patch_target.py:71-81` refuses leaked `KEYSTORE*` variables or an existing `src/ks.keystore` before starting the third-party subprocess, and passes only a non-secret allowlist to that subprocess.
* `build.sh` no longer initializes, captures, or passes keystore values.
* `utils.sh:997-1008` and `:1081-1085` make the legacy `patch`, `patch_multi`, and `split_arch` helpers refusal stubs. They contain no `eval` or key/password expansion.
* `artifact_identity.capture_inputs` now binds the public committed pin (`src/build/ci-signer.json`) rather than reading a keystore; `verify_unsigned` checks that the captured pin still equals the committed pin.

The remaining production keystore references are expected Sign-job code (`artifact_identity.cert_from_keystore`/`check_keystore_pin`, `sign_apk.py`, and `manual-patch.yml`'s Decode/Sign/cleanup steps) or recovery documentation. `src/ks.keystore` is intentionally not tracked; `capture_inputs` rejects tracked signing-material suffixes.

### Workflow and script call graph

* The only production workflow caller of `build_attempts.py`/`build.sh` is the `Patch apk` step in `.github/workflows/manual-patch.yml:202-215`. Its patch job has no `KEYSTORE_*` job/step environment and sets `PF_UNSIGNED=true` only on that step.
* `.github/workflows/ci.yml` and `batch-patch.yml` forward the three secrets through the reusable-workflow `secrets:` mapping so the called workflow can satisfy its interface; this does **not** export them into the Patch job environment. The called workflow consumes them only in Sign's Decode/Sign steps (`manual-patch.yml:339-354`).
* `resolve.sh`, `store_chain.sh`, `store_services.sh`, `source_*` scripts, `provider_scan.py`, and `.github/actions/*` have no keystore reads in the patch path. `pin_fetch.sh` sources `utils.sh` for its download helpers but does not call the refusal patch helpers.
* `explore.yml` runs `list-patches`, not `build.sh` or `patch_target.py`; `onboard-review.yml` validates onboarding data and does not build; `mcp-scout.yml` is unrelated read-only discovery; `pin-check.yml` does not invoke the patch route. No direct patch-target/build caller was found in these workflows.
* Documentation (`RECOVERY.md`, `docs/review/W15G-MAP.md`, historical changelog/knowledge entries) still mentions keystore terms, but these are not executable paths.

### `build_attempts` callers passing keys

No production caller was found that passes `KEYSTORE_*` into `build_attempts.main`. The CI/batch reusable workflow mappings are not job environments. The tests that mention keys are intentional negative/fixture coverage: `build_attempts_contracts.py` keeps an untracked fixture keystore through reset, while `test_repair.py` passes dummy key values to `patch_target.command` to prove they never become argv. The real `patch_target.py` entrypoint refuses an actual keystore file or leaked key environment before spawning Java.

## Execution-input/shadow impact

`execution_inputs.public_command` now constructs the real unsigned shape using `{"PF_UNSIGNED":"true"}` and requires `--unsigned`; it no longer constructs the old dummy credential environment. Consequently the recorded execution material and its `shadow_inputs` `effective_sha256` change once when this split is first deployed. This is expected: `effective_sha256` hashes the consumed material, including the execution observation, and subsequent runs with the same unsigned command shape stabilize.

I found no committed baseline file containing or comparing the old argv. `qualified_baselines.py` validates the receipt's effective/declaration hashes and `shadow_inputs.compare` compares the current consumed effective hash with the prior published receipt. Therefore the first post-split run will compare unequal to an old pre-split receipt (state `BUILD`, or remain `UNKNOWN` under other gates), and its successful receipt becomes the new baseline; later equivalent unsigned runs compare `UNCHANGED`. This is the expected one-time migration, not a regression.
