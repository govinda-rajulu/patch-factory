# R3 — publication evidence code review (W15g)

Scope: `git diff 74addf3..HEAD` for `shadow_inputs.py`, `qualified_baselines.py`, `release_contract.py`, and `status.py`, plus the workflow/action callers and repository-wide API-name search. Source links below point at reviewed `HEAD` (`fabb769`).

## Executive result

**No HIGH finding.** The legacy receipt/proof shape remains accepted, split-layout detection is fail-closed rather than a weaker fallback, and the new release-contract fields match the report emitted by `sign_apk.verify`. The receipt draft deliberately moves patch-only file checks into the Patch job; that is acceptable for this **shadow-only** receipt because the draft is sealed there and later checked against both the signed report's captured-input hash and unsigned-output hash. It remains same-run evidence, not an independent attestation.

One **MEDIUM** issue remains in the status page: `last_build` is now selected from individual Patch/Sign/Publish jobs by job completion time, not from a run-level aggregate. With overlapping runs, a job from an older run can win over a newer run's job, and the displayed app result is not explicitly the terminal result of one build run. This is a semantic regression risk introduced by the split.

## Findings

### MEDIUM — status `last_build` is job-time based, not run based

- **Where:** [`src/etc/status.py:411-449`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/etc/status.py#L411-L449), especially the new `JOB_RX` at [`:34`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/etc/status.py#L34).
- **What:** `build_jobs[app]` now contains all matching Patch, Sign, and Publish jobs from the recent workflow runs. It sorts those rows by each job's `completed_at`/`started_at` and uses the newest row for both `last_check` and `last_build`.
- **Why:** Before W15g there was one Patch job per app/run, so job time approximated run time. After the split there are up to three timestamps per run, and Actions permits overlapping non-publishing runs. An older run's late Publish/Sign job can therefore outrank a newer run's Patch/Sign job. More importantly, the selected row is one job, not the overall run's terminal outcome; the status card can show a successful Sign while a corresponding Publish is absent/skipped, or mix roles across runs. The existing per-app failure classification at [`:388-409`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/etc/status.py#L388-L409) is otherwise sound: failed split jobs are still recognized as app-owned when every failure has a recognized app job name.
- **Fix:** Group matched jobs by `(run.id, run_attempt, app)`, choose the newest run using a run-level timestamp (`updated_at`/`completed_at`), then derive that run's app result from its terminal role (Publish when present, otherwise Sign, otherwise Patch). Keep `last_check` as a separate latest-job view if desired. Add tests for a split run with Patch success/Sign failure/Publish skipped, a non-publishing Patch+Sign run, and two overlapping runs whose job completion order is inverted.

### LOW — status split behavior lacks direct regression coverage

- **Where:** [`tests/status_contracts.py`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/tests/status_contracts.py) still models only `Patch <id>` jobs and the old `Verify finished APK identity` failure step; `src/etc/status.py` has no direct test for Sign/Publish attribution or the timestamp issue above.
- **What/Why:** The production regex and step labels include the split names, but existing tests do not prove that Sign and Publish failures become the app row, that a nonpublishing Sign success is the app's latest build, or that a split workflow's `per_app` flag behaves correctly. This is a test gap rather than a second independently observed production failure.
- **Fix:** Extend the status fixture with `build (...) / Sign target` and `... / Publish target` rows and the run-level overlap cases described above. Also add notification fixture names for Sign/Publish (the notifier itself is generic and does not parse Patch-only names).

## Required checks

### Legacy receipts and proofs

**Pass.** `shadow_inputs.verify_receipt` keeps the legacy path when neither `Sign <target>` nor `Publish <target>` is found. It requires exactly one `Patch <target>` job, successful job status/conclusion, and the exact old mandatory step list `LEGACY_STEPS = ("Verify finished APK identity", "Verify release handoff (no publishing)", "Releasing APK files")` ([`shadow_inputs.py:26-30`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/build/shadow_inputs.py#L26-L30), [`:398-410`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/build/shadow_inputs.py#L398-L410)). Its `proof_out` legacy branch still writes **`job` + `steps`**, not the split shape ([`shadow_inputs.py:411-429`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/build/shadow_inputs.py#L411-L429)).

`qualified_baselines.verify_proof` accepts that old shape when `layout` is absent and validates the Patch job against `shadow.LEGACY_STEPS`; it rejects a `layout` key in the legacy branch ([`qualified_baselines.py:43-63`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/build/qualified_baselines.py#L43-L63)). This preserves already-published real-release proofs. Existing contract tests also exercise a legacy proof without the new receipt field.

### Split detection cannot weaken checks or reject the intended split

**Pass.** Receipt detection enters split mode if either matching Sign or Publish job exists, then requires exactly one of each Patch, Sign, and Publish role and checks all required steps, status, and conclusion ([`shadow_inputs.py:398-410`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/build/shadow_inputs.py#L398-L410)). Thus a partial or spoofed split marker cannot fall back to the weaker legacy one-job check: a lone/missing Sign or Publish causes the required three-role inventory to fail. A genuine reusable-workflow run has names `... / Patch <id>`, `... / Sign <id>`, `... / Publish <id>` and the exact `SPLIT_JOBS` steps ([`shadow_inputs.py:27-30`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/build/shadow_inputs.py#L27-L30); [`manual-patch.yml:306-365,401-436`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/.github/workflows/manual-patch.yml#L306-L365)).

`qualified_baselines.verify_proof` requires `layout == "split"`, exactly three dict entries, no legacy `job`/`steps`, and validates each entry positionally against Patch/Sign/Publish role names and exact mandatory steps ([`qualified_baselines.py:43-63`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/build/qualified_baselines.py#L43-L63)). Extra unrelated jobs in the run are allowed, as before; all inventory rows are still checked for identity and pagination completeness.

### Receipt draft binding and the legacy-vs-split check boundary

**Pass / intentional shadow-only boundary.** The Patch job creates a draft only from an `unsigned`, `signing_split` report for the target; it requires `.build-inputs.json == report["inputs"]`, re-verifies the patcher/bundle/input-APK/ledger records, computes `realized(...)`, and seals `inputs_sha256 = sha(captured)` plus `unsigned_sha256 = report["output"]["sha256"]` ([`shadow_inputs.py:566-588`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/build/shadow_inputs.py#L566-L588)). This is the requested binding over report inputs and the unsigned APK hash.

On the split Publish path, the draft is unsealed and checked against `sha(captured)` and `report["unsigned_output"]["sha256"]`; its consumed document is unsealed and its `effective_sha256` is recomputed from its material ([`shadow_inputs.py:590-624`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/build/shadow_inputs.py#L590-L624)). `release_contract.verify` has already checked the signed report, current commit, package, APK bytes/path, signature, and run binding before this path is reached.

Compared with the legacy Publish path, the split path no longer:

1. re-runs `realized(root, captured, env)` in Publish;
2. re-verifies the consumed patcher/bundle/input-APK/ledger files in Publish; or
3. regenerates prepared dependency/source snapshots locally in Publish (it uses the snapshots sealed in the draft).

That is acceptable for the stated **shadow-only** receipt because the Patch job is the only job with those files, performs the checks before sealing, and the signed hand-off binds the report to the same run/attempt and unsigned bytes. The code explicitly documents the remaining trust limit (`same-run evidence`, not independent attestation). It would not be acceptable as an independent publication attestation; no such stronger claim is made.

### Release-contract fields and callers

**Pass; no field mismatch found.** `sign_apk.verify` writes:

- `status: "verified"`, `signing_split: true`;
- `unsigned_output` as the original unsigned report's `output` record;
- `signature.certificate_sha256` and `cryptographic_verification: "passed"`;
- `signing.schemes`, `binding`, `pin`, `entries_compared`, `signature_files`, and `alignment` ([`sign_apk.py:243-247`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/build/sign_apk.py#L243-L247)).

`release_contract.verify` requires exactly those names/relationships: `signing.binding == run_binding(os.environ) == d["unsigned"]["binding"]`, positive `entries_compared`, v2 true/v4 false, a valid unsigned SHA different from signed output, and certificate equal to captured expected pin, `signing.pin`, and committed pin ([`release_contract.py:46-62`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/src/build/release_contract.py#L46-L62)). The schemes produced by `sign_apk` always have v2 true and v4 false, including the low-minSdk legacy scheme set.

The Sign job calls `release_contract.py "$TARGET"` without `--github-output` after `sign_apk.py verify` ([`manual-patch.yml:358-365`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/.github/workflows/manual-patch.yml#L358-L365). That mode performs verification but does not access `GITHUB_OUTPUT`. The Publish job's composite release action calls the same verifier with `--github-output` ([`action.yml:10-16`](https://github.com/govinda-rajulu/patch-factory/blob/fabb769/.github/actions/release/action.yml#L10-L16). GitHub supplies `GITHUB_RUN_ID` and `GITHUB_RUN_ATTEMPT` automatically to both jobs, and the report's run binding was created in the Patch job and checked again by Sign, so there is no “every publish fails” environment mismatch.
