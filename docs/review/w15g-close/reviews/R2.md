# R2 — GitHub Actions correctness review (one lens)

Scope: `.github/workflows/manual-patch.yml`, as directly dispatched and as called by
`.github/workflows/ci.yml` and `.github/workflows/batch-patch.yml`; compared with
`git -C (assistant sandbox) diff 74addf3..HEAD -- .github/`.  This is a static review;
no workflow was run on GitHub.

## Findings

### HIGH — a rerun of only `Sign` or `Publish` cannot find its upstream artifact

- **Where:** `manual-patch.yml:296`, `:328`, `:370`, `:428`.
- **What:** Every handoff name includes `${{ github.run_attempt }}`. GitHub documents that
  `github.run_id` stays the same on a rerun while `GITHUB_RUN_ATTEMPT` increments for each
  attempt ([contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#github-context)).
- **Why:** On a first attempt, Patch uploads `patch-output-<target>-<run_id>-1` and Sign
  downloads that name. If only the failed Sign job is rerun, it requests
  `...-<run_id>-2`, but Patch was not rerun and only the `-1` artifact exists. Likewise,
  rerunning only Publish requests `signed-output-...-2` although Sign's successful first
  attempt produced `...-1`. The download action's `name` is an exact artifact name and
  a single named artifact is extracted directly into the requested `path`
  ([pinned download-artifact README](https://github.com/actions/download-artifact/blob/9000827ccba6bdab643e8b6fd33ac0654aef8333/README.md#download-single-artifact)).
- **Fix:** Make retry selection explicit: either use stable, run-scoped handoff names
  and deliberately overwrite/recreate them when an upstream job is rerun, or have a
  rerun-only Sign/Publish resolve the artifact from the prior attempt (while preserving
  the attempt-bound names for fresh upstream uploads). Do not assume changing
  `run_attempt` is a retry-safe artifact selector. Test: first attempt Patch succeeds,
  Sign fails; rerun only Sign; then rerun only Publish.

The same retry design problem affects diagnostic artifacts without `run_attempt`
(`build-evidence-<target>` at `:223` and `provider-scan-<target>-<run_id>` at `:260`):
if a Patch job is rerun after either upload already succeeded, v7's immutable artifact
name can collide. The pinned upload README states that artifacts are immutable and
same-name uploads fail unless explicitly overwritten ([artifact immutability and
matrix naming](https://github.com/actions/upload-artifact/blob/cf430e030ddbb5b0abf93d22962f4752f3646cd9/README.md#not-uploading-to-the-same-artifact)).
This is a secondary retry failure, not a matrix-target collision.

### MEDIUM — Batch caller does not grant the `actions: read` requested by Publish

- **Where:** `batch-patch.yml:46-48` has `permissions: contents: write` only. The
  called workflow's Publish job requests `contents: write` and `actions: read` at
  `manual-patch.yml:401-412`. In contrast, `ci.yml:218-221` grants the reusable-call
  job both `contents: write` and `actions: read`.
- **What/why:** GitHub says permissions passed from a caller to a reusable workflow can
  only be downgraded, not elevated ([reusable workflow reference](https://docs.github.com/en/actions/reference/reusable-workflows-reference#supported-keywords-for-jobs-that-call-a-reusable-workflow)).
  Also, when a permissions map names any scope, every unspecified scope is `none`
  ([workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#permissions)).
  Therefore the Batch call's effective ceiling is `contents: write`, `actions: none`;
  the called Publish job cannot obtain `actions: read` from its own declaration.
- **Impact/fix:** Add `actions: read` to `batch-patch.yml`'s `build.permissions` so the
  caller explicitly supplies the called workflow's requested ceiling. The current
  `download-artifact` invocations are same-run named downloads and the pinned README
  says an explicit token is needed for a *different* workflow/run, so this mismatch may
  not fail the current implementation; nevertheless the declared Publish permission
  is not actually realizable under Batch and should be corrected, especially if the
  action/API path ever uses the job token ([pinned download-artifact README](https://github.com/actions/download-artifact/blob/9000827ccba6bdab643e8b6fd33ac0654aef8333/README.md#download-artifacts-from-other-workflow-runs-or-repositories)).

### LOW — signing secrets are passed to the reusable-workflow context, not
job-scoped

- **Where:** `manual-patch.yml:74-82` declares all three keystore secrets for
  `workflow_call`; both callers pass them at `ci.yml:222-225` and
  `batch-patch.yml:52-55`.
- **What:** A directly passed reusable-workflow secret is available in the called
  workflow's `secrets` context; GitHub does not provide a per-job secret declaration.
  The actual file does *not* map keystore secrets into Patch or Publish environments:
  Patch maps only optional `VT_API_KEY` for the scan (`:236-242`), Sign maps
  `KEYSTORE_B64` only in decode (`:340-347`) and password/alias only in signing
  (`:348-354`), and Publish maps none. Thus there is no observed accidental secret
  environment exposure in this diff.
- **Why it still matters:** The stated “Sign alone holds the release key” property is
  enforced by disciplined use of the context, not by workflow_call secret scoping.
  A future Patch step could reference the passed keystore secret. GitHub documents that
  callers pass named secrets to a directly called workflow and that secrets are then
  available to that called workflow ([reuse-workflows secrets](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows#passing-inputs-and-secrets-to-a-reusable-workflow)).
- **Fix (if strict job isolation is required):** Split the signing reusable workflow or
  otherwise arrange that the Patch-only reusable workflow is called without keystore
  secrets; retain the current narrow `env` mappings as defense in depth.

## Checks with no correctness finding

### Expressions, `needs`, and skipped steps

- The unbraced `if` forms (`if: inputs.publish && ...`, `if: steps...`) are valid
  conditional expressions; `${{ }}` is optional in `if`. `run-name` uses only supported
  `github`/`inputs` contexts and valid `format` plus `&&`/`||` fallback syntax. The
  `inputs` context is valid for both `workflow_dispatch` and `workflow_call`; for a
  called workflow, `github` remains the caller's context. See
  [expression syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions)
  and [contexts](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts).
- `patch.outputs.built_at` correctly maps `steps.stamp.outputs.built_at`
  (`:92-96`, stamp `:115-121`). `needs.patch.outputs.built_at` is then placed in the
  Sign and Publish job environments (`:313-315`, `:413-419`). A skipped step's outcome
  is `skipped`, and a missing step output resolves empty; the expressions for
  `resolved_ready`/`source_ready` consequently evaluate false when their verification
  step was skipped rather than throwing. Job outputs are evaluated at job completion
  and exposed through `needs` to dependent jobs ([job outputs](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/pass-job-outputs),
  [contexts: steps outcomes](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#steps-context)).
- `sign` has `needs: patch` and no status override, and `publish` has
  `needs: [patch, sign]`. GitHub applies an implicit `success()` to an `if` that does
  not contain a status function ([expressions: status checks](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions)).
  Thus a failed/cancelled Patch prevents Sign; a failed/cancelled Patch or Sign prevents
  Publish. `always()` in CI's caller build gate is intentional: it lets the build job
  inspect Plan/Resolve outcomes, while the called Patch's own normal dependency
  behavior remains intact.

### Publish and smoke gating

- Publish is restricted by both `inputs.publish` and
  `github.ref == 'refs/heads/main'`, plus the Patch connection output
  (`manual-patch.yml:401-404`). The earlier Patch guard rejects `publish=true` on a
  non-main ref (`:122-126`); Batch's fan job has the same guard (`batch-patch.yml:27-31`).
- A branch smoke with `publish=false` reaches Patch, then Sign (`needs: patch`), runs
  signed verification and the test APK/evidence uploads (`:380-399`), and skips Publish.
  The test upload conditions explicitly include `success()`. This path is expected to
  pass when scan is false (the default); requesting `scan=true` intentionally adds
  ClamAV/provider-scan work that can fail independently.
- Direct dispatch is not capped by the called-workflow rule: its job-level Publish
  `contents: write` overrides the called file's workflow default `contents: read`.
  For CI, the caller build job explicitly supplies `contents: write, actions: read`
  (`ci.yml:218-221`), so the called Publish ceiling is satisfiable. Batch is the only
  caller with the permission mismatch above.

### Artifacts (v7/v8 semantics), matrix collisions, and paths

- Both Patch and Sign handoffs use `actions/upload-artifact@v7` with
  `include-hidden-files: true`, `compression-level: 0`, `retention-days: 1`, and
  `if-no-files-found: error` (`:294-305`, `:368-379`). These are valid pinned-v7
  inputs: hidden files are otherwise excluded, compression 0 is valid/no compression,
  and retention 1 is within the documented 1–90-day range ([pinned v7 README inputs](https://github.com/actions/upload-artifact/blob/cf430e030ddbb5b0abf93d22962f4752f3646cd9/README.md#inputs)).
- The four handoff paths have workspace as their least common ancestor, so the
  downloaded artifact contains `release/`, `build-evidence/`, `shadow-evidence/`, and
  `src/targets.json`; this matches `download-artifact`'s single-name direct extraction
  to `handoff/` and the subsequent `sign_apk.py place` step. This is the documented
  multi-path/LCA behavior ([multiple paths](https://github.com/actions/upload-artifact/blob/cf430e030ddbb5b0abf93d22962f4752f3646cd9/README.md#upload-using-multiple-paths-and-exclusions)).
- Matrix/batch target IDs are unique: `batchplan.sh` rejects duplicate requested IDs,
  and the daily plan derives each selected ID once from the unique target config.
  Consequently `build-evidence-<target>`, handoff names, and test names do not collide
  between matrix entries in one run. Artifacts are scoped to a workflow run, so the
  absence of `run_id` in `build-evidence` alone is not a cross-run collision. The
  retry collision is the separate HIGH issue above.
- v8 download names and paths are used correctly, and `digest-mismatch: error` is a
  valid secure setting (`:148-152`, `:326-330`, `:426-430`). v8 defaults mismatch to
  error as documented ([pinned v8 README inputs](https://github.com/actions/download-artifact/blob/9000827ccba6bdab643e8b6fd33ac0654aef8333/README.md#inputs)).

### Concurrency and timeouts

- Patch and Publish use target-keyed groups with `cancel-in-progress: false`
  (`:86-88`, `:405-407`), so same-target work queues instead of being cancelled.
  CI's top-level `daily-poll` group also queues runs (`ci.yml:11-15`). The called
  workflow does not reuse a caller group with cancellation enabled, so it avoids the
  reusable-workflow concurrency cancellation trap documented by GitHub
  ([reusable workflow reference](https://docs.github.com/en/actions/reference/reusable-workflows-reference#supported-keywords-for-jobs-that-call-a-reusable-workflow)).
- Job timeouts are bounded and syntactically valid: Patch 60 minutes (`:97-99`),
  Sign 20 (`:306-312`), Publish 20 (`:401-412`), with 3-minute shadow operations and
  a 180-second release-receipt timeout in the composite action. No timeout creates an
  unbounded workflow run; adequacy of external download/scan duration is operational,
  not an expression or wiring defect.

## Bottom line

The split job graph and normal first-attempt path are syntactically coherent: Patch
builds unsigned output, Sign downloads/verifies/signs it, and Publish is gated to
main+publish. The two actionable workflow-level defects are (1) retry artifact
selection/name handling (HIGH), and (2) Batch's missing `actions: read` caller ceiling
(MEDIUM; potentially benign for the current same-run artifact implementation but
incorrect as declared). The secret note is a LOW hardening concern, not an observed
first-run failure.
