# W15g laser-scoped review — signing and artifact identity

Scope: `src/build/sign_apk.py` (new) and the changed helpers in `src/build/artifact_identity.py`, on `74addf3..HEAD`. I also checked the workflow hand-off because it determines whether the code can receive a legitimate artifact. Focus is the stated one lens: pin continuity, no secret exposure, exact hand-off, scheme/alignment rules, and ZIP payload preservation.

## Findings

### HIGH — `place()` resolves the hand-off symlink before checking whether it is a symlink

**Where:** `src/build/sign_apk.py:82-87` (`stage = (root / stage).resolve()` followed by `not stage.is_symlink()`).

**What:** A `handoff` symlink to another directory *inside the checkout* is resolved to its target, after which `stage.is_symlink()` is false and `stage.parent == root` can still be true. The allowlist is then evaluated against the target and `shutil.rmtree(stage)` removes that target directory. A test symlink to an in-tree directory demonstrates the predicate:

```text
root/handoff -> root/real
(stage after resolve) root/real, is_symlink=False, parent==root=True
```

This bypasses the intended “fresh, regular hand-off folder” boundary and can delete or import files from an arbitrary checkout directory. It is also an avoidable path substitution at the boundary where untrusted artifact contents enter the signing checkout.

**Why:** The existing test only covers a symlink *inside* the staged tree (`signing_split_contracts.py:410-414`), not the stage directory itself. `resolve()` must not precede the symlink check.

**Exact fix:** Keep the lexical path for validation, then resolve only after validation:

```python
stage = root / stage
ai.require(stage.is_dir() and not stage.is_symlink() and stage.parent == root,
           'hand-off folder missing')
stage = stage.resolve()
ai.require(stage.parent == root, 'hand-off folder outside checkout')
```

Better still, use `os.lstat()`/`Path.is_symlink()` on the original path and open/move files with directory-descriptor or `O_NOFOLLOW` protections if hostile same-run processes are in scope.

### HIGH — ZIP comparison trusts central-directory metadata and does not validate local headers or descriptors

**Where:** `src/build/sign_apk.py:164-182` (`entries()`), and `:192-203` (`compare()`).

**What:** `entries()` checks only the four-byte local-header magic, then takes filename/extra lengths from the local header and all entry identity/size/CRC information from `ZipInfo` (central directory). It hashes `info.compress_size` bytes but never checks:

* local-header filename, flags, method, CRC/size fields against the central record;
* whether the local header’s name is the central-directory name;
* whether a data descriptor (including optional signature and ZIP64 widths) is present and agrees with the central record;
* whether the data range and descriptor stay before the next record/central directory; or
* ZIP64 local/descriptor consistency.

The comparison intentionally drops `offset`, but it also drops all local-header and descriptor identity. A small Python experiment changed the local-header filename byte from `x` to `y` while leaving the central directory and data intact; `entries()` returned the same row and would compare equal. Thus a signer/output rewrite that altered local structural bytes can pass the “every non-signature entry” check even though the raw ZIP entry is not the same. ZIP64 offsets themselves are represented by Python `zipfile` as integers, but that is not a validation of the ZIP64 records.

**Why:** The stated invariant is raw-entry preservation, not merely central-directory payload preservation. Local-header parsing and data descriptors are explicitly in scope. `zipfile` also permits duplicate central names to be enumerated, although this code correctly rejects duplicate names at `:169`; that rejection does not repair the local-header trust issue.

**Exact fix:** Parse each local header and require its signature, filename bytes, flags, method, and structural fields to agree with the central entry (allow only the alignment-related extra-field rewrite that `apksigner` documents). Compute the local data start only after validating the name/extra lengths and bounds. For bit-3 entries, parse the optional `PK\x07\x08` descriptor in both 32-bit and ZIP64 forms and require its CRC and sizes to equal the central record; reject malformed, truncated, overlapping, or ambiguous descriptors. Include normalized local structural fields and descriptor values in each comparison row, while excluding only documented signer-owned fields. Add fixtures for a local-name mutation, descriptor mutation, ZIP64 entry, and descriptor with/without the signature marker.

Official behavior to preserve: [AOSP `ApkSigner.java`](https://android.googlesource.com/platform/tools/apksig/+/refs/heads/main/src/main/java/com/android/apksig/ApkSigner.java) says ordinary entries retain their local header/data where possible, while alignment may rewrite local extra data; therefore the fix must compare fields rather than insist on byte-identical local extra padding.

### MEDIUM — signature-file classification is case-sensitive, so lowercase `.rsa` is not treated as a signer file

**Where:** `src/build/artifact_identity.py:402` (`SIGNATURE_FILE`), used by `verify_unsigned()` at `:433-438` and by `sign_apk.compare()` at `:194-202`.

**What:** The expression recognizes `META-INF/*.SF`, `.RSA`, `.DSA`, `.EC`, `SIG-*`, and exact uppercase `MANIFEST.MF`, but `META-INF/foo.rsa` does not match. The signer’s documented behavior is to strip/replace pre-existing v1 signature structures. If a legitimate input carries a lowercase algorithm suffix that the active apksigner treats as a signature file, the signed output omits/replaces it while `compare()` treats the old file as an ordinary payload and refuses the APK. Conversely, if the tool preserves it as an ordinary resource, the code must not silently classify it as signer-owned; this needs an explicit compatibility test against the build-tools versions used.

**Why:** The review requirement specifically includes lowercase `.rsa` and `.SF` files with arbitrary signer names. The arbitrary-name `.SF` case is covered by `[^/]+[.]SF`; case handling is not.

**Exact fix:** Make the extension/prefix matching case-insensitive (`re.IGNORECASE`) if the supported apksigner behavior strips these names, and add fixtures for `META-INF/old.SF`, `META-INF/other.rsa`, `META-INF/other.dSa`, and `META-INF/SIG-old`. If apksigner intentionally treats lowercase names as ordinary entries, keep the strict expression but add a tool-version contract proving that behavior rather than guessing.

Official reference: [AOSP `V1SchemeSigner.java`](https://android.googlesource.com/platform/tools/apksig/+/refs/heads/main/src/main/java/com/android/apksig/internal/apk/v1/V1SchemeSigner.java) and the supplied `APKSIGNER-FACTS.md` document the standard `MANIFEST.MF`, `*.SF`, `*.RSA`, `*.DSA`, `*.EC`, and `SIG-*` set.

**`MANIFEST.MF` note:** Excluding `META-INF/MANIFEST.MF` is consistent with apksigner’s v1 signature stripping/generation convention, but this name is not cryptographically self-describing: an application can use it as an ordinary META-INF resource. Add an explicit fixture for a v2-only APK containing an ordinary manifest and document the supported apksigner result. Do not broaden the exclusion to arbitrary `META-INF/*` files.

### MEDIUM — `zipalign -c 4` does not verify the required 16-KiB native-library alignment

**Where:** `src/build/sign_apk.py:185-189` (manual check) and `:206-211` (`zipalign_check`).

**What:** The manual check does test stored `.so` offsets modulo 16,384, but the external verification is only `[zipalign, '-c', '4', apk]`. That checks ordinary four-byte alignment and does not ask zipalign to validate the 16-KiB `.so` page rule. The code therefore labels a 4-byte-only zipalign result as sufficient, with the stronger rule depending on a separate custom parser.

**Why:** The official syntax is `zipalign -c -P 16 -v 4 existing.apk`; `-P 16` selects the native-library page requirement. See [Android Developers — zipalign](https://developer.android.com/tools/zipalign) and [AOSP ZipAlignMain.cpp](https://android.googlesource.com/platform/build/+/refs/heads/main/tools/zipalign/ZipAlignMain.cpp). The supplied `APKSIGNER-FACTS.md` also states that older build-tools may lack `-P`; that version question must be explicit.

**Exact fix:** Run `zipalign -c -P 16 4 <apk>` (optionally `-v`) and pass `cwd=root, env=env`. Require a build-tools version known to implement `-P 16` (the supplied facts verify 35.0.0+), or fail with a clear “16-KiB checker unavailable” error while retaining the manual check as defense in depth. Also use `n.lower().endswith('.so')` in `alignment()` if case-variant native-library names are to be supported.

This is not currently a demonstrated bypass because the manual modulo check catches normal lowercase `.so` entries; it is a semantic gap and can cause false confidence or tool-version-dependent behavior.

### MEDIUM — v3.2 output is parsed and then discarded

**Where:** `src/build/sign_apk.py:48-57` (`parse_schemes`).

**What:** The regex recognizes `v3.2` lines, and build-tools 37 fixtures in this tree contain `Verified using v3.2 scheme ...: false`, but the return value only includes `v1`, `v2`, `v3`, `v3.1`, and `v4`. If a verifier ever reports `v3.2: true`, the value is silently reduced to `v3.2=False` and can equal the expected dictionary. The same pattern would silently ignore any future `vN` line.

**Why:** The required scheme contract is exact. Current 35–37 output includes v3.1/v3.2 lines and may omit the v4 line when no v4 sidecar is available; omission of v4 is correctly represented as false by the current code, but a present true v3.2 must not disappear.

**Exact fix:** Include every supported output line (`v3.1`, `v3.2`, `v4`) in the returned dictionary and expected scheme rule, with v3.1/v3.2/v4 explicitly false. Reject any unrecognized `Verified using vN scheme` line rather than dropping it. Add fixtures for 35/36/37 with v3.1 and v3.2 false, v4 false, and with the v4 line absent; add a negative v3.2=true test. Keep the existing requirement for v1/v2/v3. The current acceptance of an absent v4 line should remain false, not become a refusal, because some apksigner versions do not print it.

### MEDIUM — metadata equality includes the absolute reader path and can refuse a legitimate APK

**Where:** `src/build/sign_apk.py:240-242`; source field is assigned in `src/build/artifact_identity.py:237-255`.

**What:** The unsigned report stores `manifest.reader` as the absolute `aapt2`/`apkanalyzer` path. `verify()` requires the complete dictionary, including `reader`, to equal the patch-job report. Sign and Patch are separate Ubuntu images/jobs; a runner-image update, SDK inventory change, or different selected build-tools version can produce the same package/version/minSdk while changing only the absolute reader path. The signed APK is then refused despite unchanged metadata.

**Exact fix:** Compare only semantic metadata (`package`, `version_code`, `version_name`, `min_sdk`) and validate `reader` separately as a local diagnostic string, or store a stable reader identity (`aapt2` plus a validated build-tools version) rather than an absolute path. Keep the actual reader in evidence for diagnostics, but do not make its host path part of APK equality.

### MEDIUM — retrying only failed jobs on workflow attempt 2 rejects a legitimate attempt-1 hand-off

**Where:** `.github/workflows/manual-patch.yml:325-330` names the downloaded artifact with `${{ github.run_attempt }}`; `src/build/sign_apk.py:122` requires `unsigned.binding == ai.run_binding(env)`; the Sign job’s `needs: patch` is at `:308`.

**What:** If Patch succeeded on run attempt 1 but Sign failed, a “re-run failed jobs” operation can start Sign on attempt 2 without rerunning Patch. Sign asks for `patch-output-<target>-<run_id>-2`, while the only patch artifact is `...-1`; even if an operator makes the artifact available, `handoff()` rejects it because the report binding says attempt 1 and the current environment says attempt 2. This fails safely, but it refuses a legitimate APK and is exactly the partial-rerun case the handoff check needs to define.

**Exact fix (preserving the exact-attempt security property):** Make the workflow rerun/rebuild Patch whenever Sign is rerun, or add a dedicated same-attempt handoff regeneration job; then the artifact name and report binding are both attempt 2. If failed-job-only reruns are a supported UX, use an immutable artifact keyed by run ID plus recorded source commit/digest, explicitly authorize only a prior attempt of that same run, and change `run_binding`/workflow checks as one audited design—do not merely remove the attempt check or download an arbitrary prior artifact. Add an integration contract covering Patch attempt 1 → Sign attempt 2.

### MEDIUM (policy-dependent) — the keystore alias is placed in process argv

**Where:** `src/build/sign_apk.py:150-152` (`--ks-key-alias`, `env['KEYSTORE_ALIAS']`) and `src/build/artifact_identity.py:100-101` (`keytool -alias`, `env['KEYSTORE_ALIAS']`).

**What:** Passwords are correctly represented as `env:KEYSTORE_PASS` and are not put in argv, logs, or reports. The alias, however, is copied from a GitHub secret and put directly in argv for both keytool and apksigner. It is visible to same-host process inspection and to wrappers/tool diagnostics (the existing fake-tool test records it). A keystore alias is normally a non-secret identifier, so this is not a cryptographic key leak; it nevertheless violates the stated “alias in argv risk” if `KEYSTORE_ALIAS` is treated as secret.

**Exact fix:** Decide and enforce one policy. If the alias is non-secret, stop storing it as a secret, constrain it to a strict bounded alias grammar before invoking either tool, and document that argv exposure is intentional. If it is secret by policy, the CLI cannot hide it: use an in-process apksig/keytool API or a purpose-built wrapper that receives the alias through a protected descriptor/IPC channel and never exposes it in argv; do not attempt shell quoting as a fix. Keep passwords as `env:` references and continue suppressing raw tool output.

## Checks that passed / no finding

* `sign()` checks the decoded keystore certificate against `pinned_certificate(root)` before invoking apksigner (`sign_apk.py:137-153`), and `verify()` checks the one reported signer against the same committed pin (`:230-235`; helper `artifact_identity.py:384-386`). The live signer fingerprint therefore does not change through the normal path.
* The signing flags are spelled correctly and booleans are separate arguments: `--alignment-preserved true` and `--v1/--v2/--v3/--v4-signing-enabled <true|false>` (`sign_apk.py:41-45,150-152`). This matches the official optional-boolean parser in the supplied facts. The explicit v4 false also prevents the `.idsig` sidecar described by [Android Developers — apksigner](https://developer.android.com/tools/apksigner).
* Passwords are passed only via `env:KEYSTORE_PASS`; `subprocess.run(..., capture_output=True)` and bounded error text prevent raw apksigner/keytool output from entering logs. No alias or password is written to the evidence report. The alias argv concern is reported separately above.
* `sign()` has a `finally` cleanup (`sign_apk.py:160-161`) covering handoff failure, pin failure, tool lookup failure, subprocess failure, and output validation; the explicit workflow `Remove keystore` step is also `if: always()` (`manual-patch.yml:355-357`). A normal regular-file keystore is deleted on all tested failure paths. The only unhandled cleanup edge is an unexpected directory/permission/race at that pathname, which must not be “fixed” by recursively deleting an arbitrary directory.
* Duplicate ZIP names are rejected (`sign_apk.py:168-169`), entry order of all non-signature names is checked (`:199`), compressed/raw stored bytes and CRC/sizes are compared (`:194-198`), and ZIP64 central offsets are handled as Python integers. These are useful safeguards, but they do not replace the local-header/descriptor validation in the HIGH finding.
* `parse_schemes()` accepts normal 35–37 verbose lines with v3.1/v3.2 and also treats a missing v4 line as false. The problem is only that v3.2 true is discarded; absence of v4 should remain accepted as false.
* The minSdk source is appropriate: `artifact_identity.metadata()` reads `aapt2 dump badging`, and `sdk_metadata.parse_badging_sdk()` accepts exactly one strict `sdkVersion:` or `minSdkVersion:` declaration, not target/compile SDK. `expected_schemes()` uses `<24` versus `>=24` as required by the supplied Morphe source: legacy `v1+v2+v3` below 24, v2 only at 24+, never v4.
* The allowlist matches the workflow’s uploaded hand-off roots: `release/` (including hidden release metadata), `build-evidence/*.json`, `shadow-evidence/*.json`, and `src/targets.json`. `build.sh` writes release APK plus `.version`, `.tagprefix`, `.tagsuffix`, `.patchver`, `.applied`, `.provider`, optional `.dropped`; `build_attempts.py` adds `.fallback` and `.fallback-provider`; shadow writers use JSON. The stage-directory symlink issue is the exception.
* No ordinary allowlist mismatch was found for the documented Patch → Sign → Publish artifacts. `src/targets.json` is intentionally carried and accepted only as checkout bytes or `build_attempts.view_text(original, ident, winner)` (`sign_apk.py:92-101`).
