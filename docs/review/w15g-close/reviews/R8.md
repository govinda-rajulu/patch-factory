## Findings

### LOW — two new contract classes are below the `unittest.main()` guard and are silently omitted by direct execution

**WHERE:** `tests/signing_split_contracts.py:619-640`; `tests/status_contracts.py:346-376`.

**WHAT:** Both files call `unittest.main()` and only then define newly added classes. Running the file directly therefore reports green while omitting the tests added after the guard:

```text
python3 tests/signing_split_contracts.py -q       -> Ran 36 tests
python3 -m unittest discover -s tests -p signing_split_contracts.py -q -> Ran 38 tests
python3 tests/status_contracts.py -q              -> Ran 19 tests
python3 -m unittest discover -s tests -p status_contracts.py -q       -> Ran 23 tests
```

The omitted signing tests are the v3.2/unknown-scheme and case-insensitive signature-name checks. The omitted status tests are the new no-runs and Patch/Sign/Publish job-name/step-word checks. The repository’s current validate workflow uses discovery, so this does not currently make that workflow green incorrectly, but a reviewer/operator invoking the documented-looking `python3 tests/<file>.py` form gets a false-green result.

**FIX:** Move each `if __name__ == '__main__': unittest.main()` block to the end of the file (after every test class), then assert direct and discovery counts agree.

### LOW — shadow/recipe publication tests synthesize a “signed” APK and report instead of exercising the Sign verifier

**WHERE:** `tests/shadow_contracts.py:40-63,171-180`; callers include `tests/input_recipe_contracts.py:312-319` and the dependency chain at `tests/dependency_contracts.py:364-388`.

**WHAT:** `seal_signed_fixture()` appends the literal bytes `signed-fixture` to the unsigned APK, rewrites the report to `status=verified`, supplies a pinned certificate and `cryptographic_verification=passed`, and hard-codes signing evidence. It does not invoke `sign_apk.sign()` or `sign_apk.verify()` and does not create a cryptographically valid APK. The downstream receipt/release/qualification tests consequently prove that a hand-crafted evidence dictionary is accepted, not that a real Sign-job output can traverse that chain. The dependency test further rewrites the fake release asset row to match the synthesized report (`dependency_contracts.py:379-382`) before publishing.

There is separate real-fake-tool coverage in `tests/test_identity.py`, so this is a coverage hole rather than a claim that all signing tests are mocked.

**FIX:** Keep lightweight receipt-only fixtures where intentional, but add at least one shared integration fixture that runs the actual fake-tool `sign_apk.sign()` + `sign_apk.verify()` path, then seals the draft and feeds that resulting report into the shadow/recipe/qualification chain. Assert that tampering the APK or removing the actual Sign proof fails before receipt publication.

### LOW — `capture_inputs_fixture()` patches a removed signer function with a no-op, masking a regression

**WHERE:** `tests/shadow_contracts.py:22-28`.

**WHAT:** The helper uses `patch.object(identity, "capture_signer", lambda ..., create=True)`. `capture_signer` is intentionally gone from production, so `create=True` creates a fake function on the module for the duration of the test. If a future regression reintroduces a call to `capture_signer` in `capture_inputs()`, this helper will silently neutralize it and the keyless capture tests still pass. The comment says the old function was removed, but the test does not assert that no call occurs; it makes the old call callable again.

**FIX:** Remove the patch. If a mutation guard is desired, install a `side_effect=AssertionError("capture_signer must not be called")` (with `create=True` only because the symbol is intentionally absent); separately assert `not hasattr(identity, "capture_signer")` if removal is part of the contract.

### LOW — per-attempt `KEYSTORE*` stripping is unreachable redundancy after the wrapper’s fail-closed check

**WHERE:** `src/build/build_attempts.py:185-191,217-236`.

**WHAT:** `main()` rejects and returns immediately if any input environment key starts with `KEYSTORE` (`:188-191`). Therefore the later per-attempt comprehension `e = {k: v for k, v in env.items() if not k.startswith('KEYSTORE')}` (`:230`) can never remove anything on a reachable path. It is now redundant with the explicit boundary check, and the comment presents it as an active protection. Keeping two mechanisms makes future edits easy to misread: a caller can appear “safe” because of the strip while bypassing or weakening the earlier refusal.

**FIX:** Remove the comprehension and pass a copy of the already validated environment, or factor one named `keyless_patch_env()` helper that asserts no `KEYSTORE*` keys and sets `PF_UNSIGNED=true`; add a unit assertion for that helper. This is cleanup/maintainability, not a demonstrated secret leak.

### LOW — fake GitHub batch log format cannot exercise the Sign-marker parser

**WHERE:** `docs/review/controllers/fake_gh.py:83-86`; parser `docs/review/controllers/packet.tmpl.py:564-566`.

**WHAT:** For a batch run the fake emits `build (<app>) / Sign <app>\t...`, but the parser accepts only lines beginning `Sign <app>\t`. The configured W15g smoke list dispatches `manual-patch.yml` (whose fake job line is unprefixed), so the current packet gate is not blocked by this mismatch; however, the fake batch path cannot prove the parser accepts the reusable-workflow log shape.

**WHY:** A green controller rehearsal can fail to cover the reusable Batch Patch naming path, and a future change that feeds batch logs through `SMOKE_REQUIRE` could report a false missing marker.

**FIX:** Either make fake_gh emit the exact log prefix produced by the path under test, or make the parser accept both direct `Sign <app>\t` and the reusable `... / Sign <app>\t` form, with a test for each.
