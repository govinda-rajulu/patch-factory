# R6 — W15g round-two review (patch-factory packet W15g)

Scope: read-only review of `74addf3..f975ead`, with the requested receipt check from `fabb769`. I reviewed all round-one reports, the full changed-file diff, the workflow/code call graph, records/docs, and ran focused offline tests. No production files were edited.

## Executive result

The round-one fixes correctly address the stage-folder symlink boundary, signature-name case handling, v3.2 parsing, reader-path comparison, 16-KiB zipalign invocation, COE propagation, and the permissive release-extra allowlist. The main unresolved correctness issue is still the ZIP local-header/data-descriptor validation: the implementation checks local name and method, but still accepts a local flags mutation that disagrees with the central directory and does not parse/validate descriptors. This remains **HIGH** because the stated invariant is preservation of raw ZIP entry structure, not only central-directory payload metadata.

The f975 permissions change removes the called Publish job's unnecessary `actions: read` declaration, so the Batch caller's `contents: write` ceiling is now coherent for the current same-run named artifact downloads. The controller template still leaves `SMOKE_REQUIRE` empty, so the handover's stated `SIGNING_SPLIT_OK` smoke gate is not enforced by the default template; this is an **OPEN MEDIUM** control/documentation gap.

## Round-one findings: disposition and re-rating

### R1 — stage-directory symlink before validation

**Disposition: FIXED. Re-rated: HIGH → NONE.**

`src/build/sign_apk.py:84-88` now retains `raw = root / stage`, rejects `raw.is_symlink()` before `resolve()`, requires a directory, then checks the resolved directory remains directly under the checkout. The new code prevents an in-checkout `handoff -> real` link from being resolved and accepted. I ran a fixture with exactly that link; `place()` failed with `hand-off folder missing or a link`. The existing focused signing suite also passes (38 tests in this checkout).

### R1 — ZIP comparison trusts central metadata / lacks local-header and descriptor validation

**Disposition: OPEN. Re-rated: HIGH (unchanged).**

The patch added local-name, method, and no-descriptor local CRC/size checks (`sign_apk.py:170-200`), but it still does not require local flags to equal central flags, and it does not parse/validate data descriptors, ZIP64 local/descriptor consistency, or bounds through the descriptor/next record. A minimal fixture changing only the local flags to bit 3 while leaving the central directory unchanged is still accepted by `entries()`. This is not a merely theoretical distinction: the comparison claims non-signature entry preservation while omitting local structural fields. **FIX:** parse and validate flags/descriptor forms and bounds, and include normalized structural/descriptor evidence in the compared row, allowing only documented signer-owned/alignment extra-field changes.

### R1 — case-sensitive signature-file classification

**Disposition: FIXED. Re-rated: MEDIUM → NONE.**

`artifact_identity.SIGNATURE_FILE` is now `re.IGNORECASE` and covers arbitrary signer names with `.SF`, `.RSA`, `.DSA`, `.EC`, `SIG-*`, and `MANIFEST.MF`. Focused tests cover `other.rsa`, mixed-case `.Sf`, `SIG-old`, and negative nested/resource paths. The 38-test signing suite passes.

### R1 — `zipalign -c 4` omitted the 16-KiB page option

**Disposition: FIXED. Re-rated: MEDIUM → NONE.**

`sign_apk.py:224-234` invokes the documented argument order `zipalign -c -P 16 4 <apk>` for both unsigned and signed APKs, while retaining the signed 4-byte check and manual 16-KiB offset checks. The focused fake-tool suite passes, including the zipalign-failure test; the source call shape matches AOSP usage.

### R1 — v3.2 output was parsed then discarded

**Disposition: FIXED. Re-rated: MEDIUM → NONE.**

`SCHEMES` and both expected dictionaries now include `v3.2`; `parse_schemes()` returns it and rejects unknown scheme lines. A reported true v3.2 is retained and then fails the expected false rule. Focused tests cover false/true v3.2 and unknown v5; a direct parser check confirmed v3.2=true is present in the returned dictionary rather than silently dropped.

### R1 — absolute manifest reader path made metadata equality runner-dependent

**Disposition: FIXED. Re-rated: MEDIUM → NONE.**

`verify()` now compares semantic manifest fields while explicitly excluding only `reader` (`sign_apk.py:264-267`). The actual reader remains in evidence for diagnostics. This removes legitimate cross-runner refusal without weakening package/version/minSdk equality. The signing suite's fixtures use a tool path in the report and pass.

### R1/R2 — partial rerun selects an unavailable/wrong-attempt artifact

**Disposition: ACCEPTED (documented fail-closed trade-off). Re-rated: HIGH/MEDIUM → LOW.**

The artifact names remain attempt-scoped and `handoff()` still binds the report to `GITHUB_RUN_ID` and `GITHUB_RUN_ATTEMPT`. The error text now explicitly says to use “Re-run all jobs” and that a partial rerun cannot reuse another attempt's APK (`sign_apk.py:126-128`); status wording also tells operators to use Re-run all jobs. This deliberately refuses partial reruns rather than weakening the attempt binding. It remains an availability/operational limitation, not a security bypass. The focused test `test_handoff_refuses_another_attempt` passes. The separate immutable same-name diagnostic-artifact collision noted by R2 is likewise not silently solved; rerun-all is the documented operating procedure.

### R1 — keystore alias in process argv

**Disposition: ACCEPTED (documented policy trade-off). Re-rated: MEDIUM → LOW.**

Passwords remain `env:KEYSTORE_PASS` references and are not printed, while the alias is passed to `keytool`/`apksigner` argv as an identifier. The code explicitly avoids printing argv (`sign_apk.py:154-161`), and the records describe password handling but do not claim argv secrecy for the alias. This is acceptable only under the policy that the alias is non-secret; if the deployment treats it as secret, the finding reopens because ordinary CLI argv cannot hide it. The focused signing tests verify password non-leakage and the separate argv shape.

### R2 — Batch caller does not grant `actions: read` to called Publish

**Disposition: FIXED. Re-rated: MEDIUM → NONE.**

The f975 change removes `actions: read` from the called Publish job (`manual-patch.yml:412-415`), matching Batch's `contents: write` ceiling (`batch-patch.yml:46-48`). Publish currently downloads a same-run named artifact and does not use an Actions API/cross-run token. This is the coherent least-permission choice for the implementation under review; if a future cross-run/API download is introduced, the called job and every caller must be updated together.

### R2 — workflow-call secrets are available in the reusable-workflow context, not job-scoped

**Disposition: OPEN. Re-rated: LOW (unchanged).**

The workflow still declares all keystore secrets under `workflow_call` (`manual-patch.yml:74-80`), so the called workflow's code can reference them from `secrets` in any job even though current `env` mappings expose them only in Sign Decode/Sign. This is defense-in-depth debt, not an observed leak in this diff. **FIX:** split the Patch-only reusable workflow from the signing workflow, or otherwise remove keystore secrets from calls that execute provider code. Current focused audit tests confirm the intended narrow env mappings, but cannot enforce future code changes.

### R3 — status `last_build` is selected by job completion time, not run result

**Disposition: ACCEPTED (documented trade-off). Re-rated: MEDIUM → LOW.**

`status.py:411-449` still aggregates Patch/Sign/Publish jobs and chooses the newest non-skipped job by job time. The handover/open-work records explicitly describe this as the current status-page behavior and the product language accepts a newest-build-job view. It can still show a late job from an older overlapping run, or a successful Sign while Publish is skipped, so the semantic limitation is real; it is not a security or publication gate. **FIX (if stronger semantics are required):** group by `(run.id, run_attempt, app)`, choose a run-level timestamp, and derive the app result from Publish/Sign/Patch role precedence. Re-rated LOW because it is a display/reporting trade-off and is now documented rather than hidden.

### R3 — no direct regression coverage for split status attribution

**Disposition: OPEN. Re-rated: LOW (unchanged).**

The added tests cover the `JOB_RX` role names and new `STEP` keys (`status_contracts.py:364-376`), and the 23-test status suite passes, but they do not exercise Sign/Publish failure attribution, split-run terminal-role selection, or overlapping run/job completion order. This remains a test-coverage gap distinct from the accepted status behavior. **FIX:** add fixtures for Patch success + Sign failure + Publish skipped, nonpublishing Patch+Sign, and inverted completion order across overlapping runs.

### R4 — help probe suppresses Java exit status

**Disposition: ACCEPTED (documented fail-closed trade-off). Re-rated: LOW (unchanged).**

`build.sh:324-330` still uses `PHELP=$(java ... --help) || true` and checks for the literal `--unsigned`. The handover records the probe behavior and its safety property: a broken probe cannot create a successful patched APK because the real patch subprocess still runs and checks its exit code. It can delay the failure or give less precise diagnostics, but is not a signing bypass. **FIX (optional hardening):** check `command -v java` and preserve/validate the help exit status.

### R4 — stale META-INF signature entries are recorded, not rejected

**Disposition: ACCEPTED (intentional signer-owned-file policy). Re-rated: LOW / observation (no dropped old gate).**

`verify_unsigned()` records signature-file names and Sign excludes the case-insensitive signer-owned set from the payload comparison. The prior verifier did not require an unsigned APK to contain no v1 entries; apksigner is responsible for replacing/stripping the signer-owned structures. The docs now state the split's signer-file exception. Keep an explicit compatibility fixture for the supported apksigner versions, but this is not an open regression.

### R5 M1 — COE was not propagated from Patch to Sign/Publish

**Disposition: FIXED. Re-rated: MEDIUM → NONE.**

Patch, Sign, and Publish now use the same guarded expression for `COE` (`manual-patch.yml:104,316,420`): `keep_going && !publish` otherwise `vars.COE`. `input_recipe.create()` records only the boolean effect, and Sign/Publish re-compute against the same environment value. The relevant shadow/qualification suites pass (45 and 66 tests; recipe behavior is covered in the existing input-recipe tests).

### R5 L1 — direct `release/` extras accepted by handoff regex

**Disposition: FIXED. Re-rated: LOW → NONE.**

`STAGED` now admits only APKs and bounded release metadata names, not arbitrary direct `release/*` files (`sign_apk.py:77`). A manual fixture with `release/extra.txt` was rejected as an unexpected file. The generated producers (`.version`, `.tagprefix`, `.tagsuffix`, `.provider`, `.patchver`, `.applied`, and optional fallback/drop metadata) remain covered by the allowlist.

## Fresh cross-file pass

### HIGH — ZIP local-header/descriptor contract remains incomplete

**WHERE:** `src/build/sign_apk.py:170-200`, consumed by `compare()` and then `release_contract.verify()`; workflow `Verify signed APK` at `.github/workflows/manual-patch.yml:358-365` is the publication path.

**WHAT:** `entries()` reads identity/CRC/sizes from `ZipInfo` central-directory records and validates only selected local fields. It does not verify local flags against central flags or parse data descriptors (including signed/unsigned, ZIP32/ZIP64 forms), descriptor values, or record boundaries. A local flags bit-3 mutation is accepted while the central record remains unchanged. `compare()` therefore allows raw local structure to differ while `verify()` and `release_contract` claim non-signature preservation.

**WHY:** This crosses the ZIP parser and release-contract boundary: the downstream report field `entries_compared` is treated as proof by `release_contract.py:52-54`, but the proof is weaker than the docs' “every non-signature entry byte-identical” claim. Central metadata alone cannot establish local-header/descriptor preservation.

**FIX:** Parse each local header's flags/method/name/structural fields and require central agreement, then parse descriptor variants and bounds before hashing data. Exclude only documented apksigner-owned alignment extra-field changes. Add fixtures for local name/flag/method/CRC mutation, signed/unsigned descriptors, ZIP64 records, truncation, overlap, and next-record/central-directory bounds.

### Cross-file permissions check — PASS after f975

`batch-patch.yml:46-48` supplies `contents: write`; f975 removes the unnecessary `actions: read` declaration from called Publish (`manual-patch.yml:412-415`). The current Publish path uses same-run named artifact download, not a cross-run/API action read. No permissions mismatch remains in the reviewed implementation. A future cross-run/API download would need a coordinated caller/callee permission change.

### MEDIUM — controller template does not enforce the claimed `SIGNING_SPLIT_OK` smoke gate

**WHERE:** `docs/review/controllers/packet.tmpl.py:91` sets `SMOKE_REQUIRE = ()`; checks are gathered at `:560-600` but an empty tuple produces no required markers. Handover claims every enabled smoke prints `SIGNING_SPLIT_OK` (`HANDOVER-2026-10-31-W15g.md:47-53`), and Sign prints it at `src/build/sign_apk.py:274-278`.

**WHAT:** The marker is printed by Sign, but the generic controller does not require it unless a generated packet overrides the empty tuple. The `why` check at `:590-591` is vacuous when `SMOKE_REQUIRE` is empty; a smoke could pass the controller without proving the Sign marker was present. Even if configured, the implementation scans the combined `gh run view --log` text (`:542-544`) rather than a Sign-job log, so provider/patch output containing the same marker could satisfy the substring test.

**WHY:** This is a cross-file control mismatch: the handover presents the marker as a gate, while the checked-in controller template only provides optional infrastructure. It is especially relevant because the controller is the documented merge gate for smoke runs.

**FIX:** Set `SMOKE_REQUIRE = ('SIGNING_SPLIT_OK ',)` in the actual W15g controller configuration, or make the template enforce that marker for the split workflow by default; fetch/inspect the Sign job's logs or, preferably, use the Sign job conclusion/evidence rather than a combined-log substring. Add fixtures proving a missing Sign marker stops the smoke and a provider-log spoof does not satisfy it.

### MEDIUM — current records contain an obsolete throwaway-key plan statement

**WHERE:** `docs/review/SIGNING-SPLIT.md:9-15` says the Patch job makes a throwaway BKS key and runs identity/release checks against that signer; current code/workflow instead sets `PF_UNSIGNED=true`, removes keystore decoding from Patch, and checks the committed public pin in `artifact_identity.py`.

**WHAT:** The same document later has a W15h note and W15g section correcting the design, so this is historical plan text rather than an executable defect. However, its unqualified “Plan, three jobs” section is directly contradicted by the implementation and by the later “Implemented as designed” text.

**WHY:** Reviewers following the record can infer a throwaway signer still exists, misunderstand the unsigned report contract, or look for a keystore artifact that is intentionally absent. This is a documentation/control-plane inconsistency.

**FIX:** Mark lines 9-15 explicitly as superseded design, or rewrite the current plan section to the implemented no-key Patch / first-party Sign behavior. Keep the W15h/W15g historical decision as a dated record.

### LOW — caller/job names and report fields are coherent, but status test scope is narrower than production

**WHERE:** `shadow_inputs.SPLIT_JOBS` (`src/build/shadow_inputs.py:28-30`) matches workflow job names `Patch`, `Sign`, `Publish` and mandatory step names exactly; `status.JOB_RX`/`STEP` match the split workflow names; `sign_apk.verify` report fields match readers in `release_contract.py`, `release_notes.py`, and `shadow_inputs.py`.

**WHAT:** No naming or report-field mismatch was found. The workflow's `SIGNING_SPLIT_OK` marker also exactly matches the string printed by `sign_apk.py`; only the controller enforcement gap above remains. The upload/download artifact names and all four LCA paths match, and missing `shadow-evidence/` does not prevent the multi-path handoff because release/build-evidence are present and upload-artifact computes the common root across matched paths.

**WHY:** This is recorded as a cross-file pass, not an actionable defect. The only residual concern is test scope: status tests prove role regex/step dictionary membership, not complete split-run result semantics (already listed as the R3 LOW coverage finding).

**FIX:** No production fix for the coherent contracts; add the split status fixtures under the R3 LOW item.

### LOW — docs overstate `--unsigned` probe success semantics

**WHERE:** `HANDOVER-2026-10-31-W15g.md:20-23` and `src/build/build.sh:324-330`.

**WHAT:** The handover says the help probe stops without `--unsigned`, which is true, but does not disclose that the probe's Java exit status is intentionally ignored. The real invocation remains checked, so this is diagnostic wording, not a bypass.

**WHY:** Operators may interpret a probe pass as proof that Java/JAR execution succeeded, when it proves only that captured output contained the option string.

**FIX:** Add “the probe is output-based; the real patch command remains the authoritative exit-status check,” or implement the LOW hardening from R4.

## Cross-file checks that passed

* **Workflow/job names:** `Patch`, `Sign`, and `Publish` exactly match `SPLIT_JOBS`; mandatory step names exactly match workflow steps (`Verify unsigned APK identity`, `Sign APK`, `Verify signed APK`, `Verify release handoff (no publishing)`, `Releasing APK files`).
* **Artifact names:** Patch uploads `patch-output-${target}-${run_id}-${attempt}` and Sign downloads the same; Sign uploads `signed-output-${target}-${run_id}-${attempt}` and Publish downloads the same. All downloads use `digest-mismatch: error`.
* **Upload LCA:** the four handoff paths are `release/`, `build-evidence/`, `shadow-evidence/`, and `src/targets.json`, so the common root is the checkout; downloaded extraction into `handoff/` yields the expected top-level paths. `shadow-evidence/` is advisory and may be absent; the handoff has required release/build-evidence paths and does not require the advisory upload to exist separately.
* **ZIPAlign:** `zipalign_check` uses `-c -P 16 4 <apk>` for page checks and `-c 4 <signed>` for ordinary alignment, with correct ordering.
* **Report fields:** `sign_apk.verify` writes `status`, `signing_split`, `unsigned_output`, `signature`, `signing` (including `schemes`, `binding`, `pin`, `entries_compared`, `zipalign`, `signature_files`, and `alignment`), and updated `output`; `release_contract` reads the required subset, `release_notes` reads `manifest`/`signature`/`output`, and `shadow_inputs` binds the draft to `unsigned_output.sha256`. No producer/reader field-name mismatch was found.
* **Sign marker:** `SIGNING_SPLIT_OK` is printed in Sign, but actual enforcement is the controller finding above because the checked-in `SMOKE_REQUIRE` default is empty.
* **Docs:** README, SECURITY, and HANDOVER describe the implemented keyless Patch / isolated Sign / write-only Publish boundary. The stale throwaway-key language is confined to the initial plan section of SIGNING-SPLIT and is called out above.
