# R5 — W15g Sign → Publish hand-off (one lens)

## Scope and conclusion

I reviewed the workflow and code in the fresh-checkout path, then ran the focused
fallback/signing contract suites and small `view_text`/allowlist experiments. The
handoff is intentionally **not** a complete copy of the Patch runner: it carries
only `release/`, `build-evidence/`, `shadow-evidence/`, and `src/targets.json`.
That is sufficient for the Sign and Publish jobs because the other files they
need are committed files in their fresh checkout, or are already embedded in the
identity report/receipt draft.

The material exception is **COE propagation (MEDIUM)**: `input_recipe.create`
binds whether `COE` was set, but Sign and Publish do not receive the Patch job's
`COE`. A non-publishing `keep_going` run (or a repository `vars.COE`) can
therefore create a report whose recipe says `continue_on_error: true`, then fail
Sign's `release_contract.py` when it recomputes the recipe with no COE. This is
not a normal `publish=true`/`keep_going=false` run, but it is a real cross-job
contract hole. See [Fix M1](#m1).

## Boundary and exact readers

### Patch upload and `place()`

The Patch job uploads the four paths, with hidden files included:
[manual-patch.yml#L292-L305](../../../../.github/workflows/manual-patch.yml#L292-L305).
The Sign and Publish jobs download that artifact to `handoff/` and call
`sign_apk.py place` ([manual-patch.yml#L325-L334](../../../../.github/workflows/manual-patch.yml#L325-L334),
[manual-patch.yml#L425-L434](../../../../.github/workflows/manual-patch.yml#L425-L434)).
`place()` accepts only the following relative paths:
[sign_apk.py#L75-L109](../../../../src/build/sign_apk.py#L75-L109):

* `release/<one path component>` (including hidden metadata and the APK);
* `build-evidence/<name>.json`;
* `shadow-evidence/<name>.json`; and
* `src/targets.json`.

It rejects symlinks, nested paths, and all other handoff files. It also requires
an APK and `build-evidence/<target>.json`, and refuses a non-fresh checkout.
For a carried target view, it reads the staged identity report's
`inputs.winner`, imports `build_attempts.view_text`, and accepts/writes the
carried target file only when it is exactly the checkout's original bytes or the
computed winner view.

### Sign job

1. **`sign_apk.py handoff`** reads the carried identity report, `git HEAD`,
   `src/build/ci-signer.json` (the committed public certificate pin), exactly one
   `release/*.apk`, and the six mandatory metadata files
   `.version`, `.tagprefix`, `.tagsuffix`, `.provider`, `.patchver`, `.applied`:
   [sign_apk.py#L112-L130](../../../../src/build/sign_apk.py#L112-L130).
   It reads `GITHUB_RUN_ID` and `GITHUB_RUN_ATTEMPT` through
   `artifact_identity.run_binding` and checks the source commit, target, APK
   bytes/path, and pin.
2. **`sign_apk.py sign`** repeats handoff, reads the decoded temporary
   `src/ks.keystore`, `KEYSTORE_PASS`, `KEYSTORE_ALIAS`, and uses `keytool` plus
   the SDK's `apksigner`. It reads `ANDROID_HOME`/`ANDROID_SDK_ROOT` and
   `PATH` for tool discovery, and the report's minimum SDK. It deletes the
   keystore in `finally`: [sign_apk.py#L133-L162](../../../../src/build/sign_apk.py#L133-L162),
   [artifact_identity.py#L77-L121](../../../../src/build/artifact_identity.py#L77-L121).
3. **`sign_apk.py verify`** reads the report, signed `release/*.apk`, unsigned
   `signing/*.apk`, the committed signer pin, and SDK `apksigner`/`zipalign`
   (again via `ANDROID_HOME`/`PATH`). It verifies the signer, schemes, ZIP
   entry bytes/order/alignment, and APK metadata, then writes the verified
   `build-evidence/<target>.json`: [sign_apk.py#L214-L254](../../../../src/build/sign_apk.py#L214-L254).
   It explicitly requires no keystore and no `KEYSTORE*` environment variable.
4. **Sign's `release_contract.py` (no `--github-output`)** re-verifies the report,
   target, commit, input recipe, signing binding, APK and release metadata. The
   input-recipe recomputation reads the fresh checkout's `src/targets.json`, all
   candidate/extra `src/patches/*/include-patches` and `exclude-patches`, option
   JSON and declared resources, the shared build/workflow files listed in
   `input_recipe.SHARED`, `docs/obtainium.json`, `src/build/helper/apps.json`,
   and admitted source-fallback evidence. It does **not** need the Patch
   runner's root `.build-inputs.json`, `download/`, bundles, JARs, or
   `.requested`; those are represented in `report['inputs']` and are not
   re-read by this path: [release_contract.py#L33-L115](../../../../src/build/release_contract.py#L33-L115),
   [input_recipe.py#L131-L210](../../../../src/build/input_recipe.py#L131-L210).

### Publish job and composite release action

The Publish job has the signed handoff plus a fresh checkout, and the action
runs `release_contract.py TARGET --github-output`, then ncipollo, then the
shadow receipt step: [release/action.yml#L10-L37](../../../../.github/actions/release/action.yml#L10-L37).

* `release_contract.verify()` reads the same report, `src/targets.json`, fresh
  checkout recipe files, release APK and metadata, and optional
  `release/.dropped`, `release/.fallback`, and `release/.fallback-provider`.
  It requires the signed report, same run/attempt, committed certificate pin,
  package/SDK/architecture, and exact APK bytes: [release_contract.py#L33-L115](../../../../src/build/release_contract.py#L33-L115).
* `release_notes.snapshot()` is data-only, but `render()` calls `works_on()`,
  which reads `src/targets.json` to determine the MicroG note:
  [release_notes.py#L65-L82](../../../../src/build/release_notes.py#L65-L82),
  [release_notes.py#L324-L342](../../../../src/build/release_notes.py#L324-L342).
* `inventory()` reads the public release inventory with `gh api`, preserving
  only `PATH`/`HOME` plus `GH_TOKEN` or `GITHUB_TOKEN` in the child environment:
  [release_notes.py#L137-L163](../../../../src/build/release_notes.py#L137-L163).
  `publish_guard()` uses the inventory and, for a fallback with no structured
  prior primary, reads the configured primary's committed
  `src/patches/<patch_dir>/include-patches`; `previous_release()` parses the
  same inventory rows and does no additional file read:
  [release_notes.py#L165-L175](../../../../src/build/release_notes.py#L165-L175),
  [release_notes.py#L181-L235](../../../../src/build/release_notes.py#L181-L235),
  [release_notes.py#L246-L278](../../../../src/build/release_notes.py#L246-L278).
* `--github-output` requires automatic `GITHUB_OUTPUT`, may append to
  `GITHUB_STEP_SUMMARY`, runs the suffix/run check, and emits `apkpath`, `tag`,
  `name`, `body/notes`, and `summary` for ncipollo:
  [release_contract.py#L129-L164](../../../../src/build/release_contract.py#L129-L164).
  ncipollo receives the exact APK path/tag/body and is configured not to
  overwrite a repeated tag: [release/action.yml#L18-L33](../../../../.github/actions/release/action.yml#L18-L33).
* `shadow_inputs.py receipt` re-runs release verification, reads
  `build-evidence/<target>.json` and the carried
  `shadow-evidence/<target>-receipt-draft.json`, validates the sealed draft's
  input/evidence digests, then reads GitHub's tag, release assets, and tag
  commit through the API (the later baseline verifier, not this Publish step,
  checks workflow run/jobs). It does not download the APK and does not re-read
  `.build-inputs.json`, `download/*.apk`, JARs, bundles, `.requested`, or
  execution-inputs directly; the draft carries their consumed
  evidence. It writes/uploads a JSON publication receipt after the release is
  confirmed: [shadow_inputs.py#L590-L681](../../../../src/build/shadow_inputs.py#L590-L681),
  [shadow_inputs.py#L340-L430](../../../../src/build/shadow_inputs.py#L340-L430).

artifact only on non-publishing scans; it is not in the Sign/Publish handoff.
`lost_patches.py` writes root `.dropped`, which `build.sh` converts to the
allowlisted `release/.dropped`; root `.dropped` itself is not uploaded. A
failed-attempt log is under the private temporary attempt directory, not in the
handoff. No current producer writes a nested `release/` file or a non-JSON file
under either evidence directory. Note that the regex permits *any* direct file
under `release/`; later contract checks still require exactly one APK and the
known metadata, while ncipollo is given only the APK path.

## Fallback target-view experiments

`build_attempts.py` captures `original = src/targets.json` once, and every pinned
attempt calls `view(root, ident, name, original)`, whose only write is exactly
`view_text(original, ident, name)`: [build_attempts.py#L94-L108](../../../../src/build/build_attempts.py#L94-L108),
[build_attempts.py#L185-L243](../../../../src/build/build_attempts.py#L185-L243).
A failed attempt calls `reset()`, which deletes untracked attempt output and
`git checkout -- .` restores tracked files before the next attempt:
[build_attempts.py#L54-L72](../../../../src/build/build_attempts.py#L54-L72).

I ran `tests/build_attempts_contracts.py` (18 tests, pass) and
`tests/signing_split_contracts.py` (36 tests, pass), plus a direct experiment
that produced the expected pinned views (`a` retained its override and pin;
`b` retained its fallback override and pin).

| Scenario | Result |
|---|---|
| `primary_view` (one primary with overrides) | **exact**: `None` is replaced with that primary; the target is pinned and resolver can only report that winner. |
| provider-pinned (`PF_PROVIDER`) | **exact**: the sole planned candidate is pinned before build. |
| failed primary → fallback | **exact**: reset restores original bytes; fallback writes `view_text(original, ident, fallback)`. The contract test asserts the fallback override remains. |
| a `view()` written for a failed attempt, reset, then a later primary wins | **exact for actual workflow**: reset restores original, and the later pinned primary writes a fresh view from the same captured original. In the one-primary-with-overrides case, the first attempt is already that primary, so a later success is a fallback; with multiple primaries, the first attempt is unpinned and later primary attempts are the ones that call `view()`. |

The code does not separately assert `winner == name` after `build.sh`, but the
actual pinned path sets the target's `pin`, and `resolve.sh` filters candidates
to that pin ([resolve.sh#L25-L35](../../../../src/build/resolve.sh#L25-L35)). Thus the
successful workflow's carried copy is `view_text(original, ident, winner)`;
this statement is about the real `build.sh`/`resolve.sh` path, not an arbitrary
fake build script.

## Findings and fixes

### M1 — MEDIUM — COE is not part of the Sign/Publish environment

* **WHERE:** Patch job sets `COE` at
  [manual-patch.yml#L100-L109](../../../../.github/workflows/manual-patch.yml#L100-L109);
  `input_recipe.create()` stores `continue_on_error: bool(COE)` at
  [input_recipe.py#L203-L210](../../../../src/build/input_recipe.py#L203-L210);
  Sign and Publish omit COE, and `release_contract.verify()` calls
  `input_recipe.verify()` without an explicit environment at
  [release_contract.py#L41-L46](../../../../src/build/release_contract.py#L41-L46).
* **WHAT:** A Patch run with `COE` true records a recipe different from the
  Sign/Publish recomputation (false), so release handoff verification can fail
  with `input recipe: local inputs changed since capture`. `keep_going` is
  forbidden when publishing, which limits exposure, but nonpublishing Sign
  still runs the contract and `vars.COE` can also make a publish Patch true.
* **WHY:** The exact runtime switch that changed the patcher argv is treated as
  a captured input, then silently dropped at the job boundary.
* **FIX:** Propagate one explicit boolean output from Patch to Sign and Publish
  (or a job-level `COE` expression using the same guarded expression), and pass
  the environment explicitly into `input_recipe.verify`. Do not propagate any
  signing secret; only the boolean `COE` value is needed.

### L1 — LOW — direct `release/` extras are accepted by the path regex

* **WHERE:** [sign_apk.py#L75-L87](../../../../src/build/sign_apk.py#L75-L87).
* **WHAT:** Any direct `release/<name>` file, including an unexpected log or
  receipt, passes `place()`; only nested release paths are rejected.
* **WHY:** The regex is a path-shape filter, not an exact release-file manifest.
  Current producers write only the expected direct files, and the release
  contract/ncipollo path prevents an extra file from becoming the published
  APK, so impact is limited to handoff clutter/tamper surface.
* **FIX:** Optionally reject release names against `*.apk` plus the six mandatory
  metadata names and the three optional fallback/drop names, or record/refuse
  unknown direct files before moving them.

No HIGH finding was established: all required release metadata, identity reports,
shadow draft JSON, run bindings, fresh-checkout recipe sources, and publication
authorization are present at the step that reads them. The focused tests and
experiments above did not reproduce a target-view or allowlist failure.
