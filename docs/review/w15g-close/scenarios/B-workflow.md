## Findings

### HIGH — `build-evidence-*` and `provider-scan-*` artifact names are not attempt-scoped

- **Evidence:** `manual-patch.yml:223` is `build-evidence-${{ inputs.target }}`; `:260` is `provider-scan-${{ inputs.target }}-${{ github.run_id }}`. All run-scoped handoffs elsewhere include `github.run_attempt` (`:296,330,372,386,394,432`).
- **Impact:** GitHub artifact uploads are immutable within a workflow run. A “Re-run all jobs” attempt can reach an upload with a name already uploaded by attempt 1; this can fail a legitimate rerun before a new handoff is available. The scan variant is optional, but the build-evidence upload occurs on every successful Patch, so the issue is general. This does not select a stale APK for Publish—the exact handoff names and `sign_apk.py` binding checks fail closed—but it can break recovery/install-over and requires manual cleanup/new run.
- **Smallest fix:** rename both to `…-${{ github.run_id }}-${{ github.run_attempt }}`. Update `tests/provider_scan_contracts.py` and `docs/review/controllers/packet.tmpl.py:580` for the provider scan name; update any artifact-prefix readers if exact names are expected. Keep the existing retention policies.

## First real main run: what branch smoke does **not** exercise

1. `Publish <target>` at `manual-patch.yml:403-445` and its `contents: write` token.
2. Signed handoff upload/download (`:368-381` and `:429-438`) and the signed artifact digest check.
3. `.github/actions/release/action.yml:10-48`: release-contract `--github-output`, GitHub release/tag creation, APK upload, and receipt recording.
4. `publish-<target>` concurrency (`manual-patch.yml:407-409`) and the main-only `internet_error == '0'` gate in the actual Publish job.
5. `qualify-baselines.yml`’s `workflow_run` path for a successful main `Manual Patch`, `CI`, or `Batch Patch` run (`qualify-baselines.yml:3-7`); qualification demands split Patch/Sign/Publish job proof.
6. CI-only prepared dependency/source packet consumption (`ci.yml:226-230`), because packet smoke uses direct dispatch and leaves `resolved_requested` at its default false.
7. A whole Batch matrix with `fail-fast: false`, caller permission ceiling, and per-target publish jobs (`batch-patch.yml:41-55`).

The first Telegram publish can thus be green through Patch and Sign while still failing in the untested release action, write-token/API path, signed handoff transfer, receipt, or qualification chain. The static contract has no evidence that any of these main-only steps have run successfully.
