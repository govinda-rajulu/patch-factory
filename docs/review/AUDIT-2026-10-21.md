## Security

1. CRITICAL, verified by the assistant: the patcher JVM runs third-party patch bundles in the
   job that holds a write token (`manual-patch.yml` job env `GITHUB_TOKEN`, `contents: write`)
   and the signing key: the keystore is decoded before the patch step and `patch_target.py`
   passes `--keystore-password=` on the patcher's command line. A bad bundle could push to the
   repo or copy the key. Fix (W15d, owner yes first): patch in a job with no secrets and a
   read-only token; sign and publish in a separate job that runs no third-party code.
2. HIGH, verified (log `PATCHER_VERIFIED ... GitHub latest stable; no fixed version pin`): the
   patcher is whatever "latest" is at build time. GitLab extra bundles have no expected digest
   (`extra_bundle.py`, agent). Fix (W15e): pin version and sha256; the Tooling watch opens the
   bump pull request with a short list of new and removed CLI options and a test build.
3. Not a finding (agent said HIGH; re-read by the assistant): `lost_patches.py` drops a chosen
   name only when the bundle no longer offers it, at most max(3, a quarter), names each one
   (PATCH_DROPPED, `.dropped` ledger) and refuses with `strict_patches`. This is the owner's
   rule of 10 Oct 2026 (W13: piko made two names always-on and every Instagram build failed).
4. MEDIUM, agent: `nointerp.sh` misses one-line `run:` and contexts other than inputs; `ci.yml`
   gives write scopes to its plan job; `preparing/action.yml` interpolates an input into `pip`.
5. Fine, agent: no `pull_request_target`/`issue_comment`; every action pinned by sha; both
   containers pinned by digest; artifacts checked by digest; checkout credentials off in builds.
